# ImpactMap: локальный анализатор

Rust CLI для статического анализа локальных зависимостей Rust и Python.
Не использует ИИ, API-ключи или сеть во время анализа. Не запускает код,
Cargo-команды, build scripts, Python или другие процессы из анализируемого
репозитория. Python устанавливать для работы анализатора не нужно.

## Сборка и запуск

Нужны актуальный стабильный Rust и системный компоновщик для выбранного Rust
toolchain. Поддерживаются Windows и Linux. Все команды ниже выполняются из
корня ImpactMap и одинаковы для обеих ОС.

Первоначальная загрузка зависимостей (требует сеть только при пустом кеше Cargo):

```text
cargo fetch --manifest-path analyzer-rs/Cargo.toml --locked
```

После этого сборка, проверки и запуск доступны без сети:

```text
cargo build --manifest-path analyzer-rs/Cargo.toml --release --locked --offline
cargo test --manifest-path analyzer-rs/Cargo.toml --locked --offline
cargo run --manifest-path analyzer-rs/Cargo.toml --release --locked --offline --quiet
```

Передайте один UTF-8 JSON-объект через stdin и закройте stdin (EOF). Процесс
выдаст один JSON-объект и перевод строки в stdout, затем завершится.
`--quiet` убирает сообщения Cargo; сам анализатор не печатает логи в stdout.
Собранный исполняемый файл находится в `analyzer-rs/target/release/` и называется
`impactmap-analyzer` (в Windows — `impactmap-analyzer.exe`). Его можно запускать
напрямую без Cargo, кеша зависимостей и сети.

Пример автоматического запуска через Python 3 (Python здесь нужен только как
пример вызывающей программы; команда одинакова в PowerShell и Linux shell):

```text
python -c "import json,subprocess; subprocess.run(['cargo','run','--manifest-path','analyzer-rs/Cargo.toml','--release','--locked','--offline','--quiet'],input=json.dumps({'protocol_version':1,'repo_path':'.','changed_files':['analyzer-rs/src/python.rs']}),text=True,check=True)"
```

## Протокол v1

Вход:

```json
{
  "protocol_version": 1,
  "repo_path": "/path/to/repository",
  "changed_files": ["src/main.rs"]
}
```

`repo_path` — существующий локальный каталог (абсолютный или относительно
текущего рабочего каталога). `changed_files` — пути относительно этого каталога.
Принимаются `/` и `\`; абсолютные пути и выход через `..` запрещены.
Обратный слеш внутри JSON нужно экранировать как `\\`.

Пример структуры ответа (конкретные связи зависят от исходников):

```json
{
  "protocol_version": 1,
  "changed_files": ["src/main.rs"],
  "affected_files": [
    {"path": "src/lib.rs", "distance": 1, "reason": "depends on changed file"}
  ],
  "edges": [
    {"from": "src/lib.rs", "to": "src/main.rs", "relation": "imports"}
  ],
  "warnings": []
}
```

`from` использует/импортирует `to`. Поэтому изменение `to` влияет на `from`.
`mod` также создаёт такую зависимость от файла объявленного модуля.
`affected_files` вычисляется обратным обходом графа: `distance` — минимальное
число связей до любого изменённого файла. Сами изменённые файлы исключены из
`affected_files`, даже при циклах. `reason` всегда `depends on changed file`.

`edges` содержит весь обнаруженный граф, в том числе при пустом `changed_files`.
При сравнении снимков он также может включать исторические связи с удалёнными
целями, если импорт по-прежнему присутствует; это отмечается в limitations.
Все файловые пути в ответе относительные, с `/`. Результаты отсортированы,
дубликаты и связи файла с самим собой удалены; порядок обхода каталогов на
результат не влияет. `affected_files` сортируется по пути, не по расстоянию.

При некорректном JSON, версии протокола, пути изменения или `repo_path` процесс
возвращает код 1 и тот же формат ответа: версия 1, пустые списки файлов/связей
и описание ошибки в `warnings`. Успешный, в том числе частичный анализ с
предупреждениями возвращает код 0. Отсутствующий/удалённый изменённый файл
остаётся в `changed_files`, но его зависимости могут не восстановиться:
анализируется текущее дерево, без Git-истории.

## Что поддерживается

- Rust: синтаксический разбор через `syn`; `mod foo;`, `foo.rs` и `foo/mod.rs`,
  inline-модули, строковый `#[path]` внутри репозитория, вложенные модули,
  `use` с `crate`, `self`, `super`, группами и переименованиями. Учитываются
  объявленные символы и имена импортов, чтобы неизвестное имя не создавало
  ложную зависимость от корня crate.
- Rust-цели: `[lib]` и `[[bin]]`/`[[test]]`/`[[example]]`/`[[bench]]` с путями
  из локальных `Cargo.toml`, стандартные `lib.rs`/`main.rs`, файлы целей в
  `src/bin/`, `tests/`, `examples/`, `benches/`. Локальные library crate
  сопоставляются по имени из манифеста; ограничения Cargo-resolution
  сопровождаются предупреждением.
- Python: синтаксический разбор через RustPython Parser; `import`, `from`,
  несколько импортов, aliases, многострочные выражения и импорты внутри
  функций/классов/условных блоков. Локальные модули `.py`, пакеты
  `__init__.py`, относительные импорты и цепочки инициализаторов пакетов.
  Кандидаты корней абсолютных импортов: каталог репозитория и `src/`.
- Общий граф для обоих языков, несколько изменённых файлов, циклы,
  транзитивное влияние, UTF-8 и BOM.

## Ограничения первой версии

Это статический граф файлов, а не компилятор, интерпретатор или обещание полного
runtime-графа. Синтаксические импорты учитываются даже в неисполняемых ветках.
Неопределённость сообщается в `warnings`, результаты могут быть неполными
или консервативно включать кандидатов.

- Rust: не раскрываются макросы, `include!`, build scripts, `cfg` и feature
  flags, glob/re-export chains, extern crate aliases и Rust 2015 semantics.
  Cargo metadata/resolver не запускается: переименованные зависимости,
  workspace inheritance и нестандартная автонастройка целей могут требовать
  ручной проверки. Файлы без известного crate root пропускаются с пояснением.
  `#[path]` на inline-модуле не поддерживается. Обычные ссылки на символы без
  `use` (например `crate::foo::run()`) не являются частью этой версии.
- Python: не исполняются `sys.path`, import hooks, `__all__`, динамические
  импорты и код пакетов. Для `from package import name` файл подмодуля может
  быть затенён атрибутом пакета — кандидат и предупреждение возвращаются
  вместе. Для импорта символа из модуля записывается зависимость от модуля,
  а возможные реэкспорты отмечаются. Namespace packages сопровождаются
  предупреждениями. Нестандартные source roots, compiled extensions и
  Python-синтаксис, не поддерживаемый RustPython Parser 0.4, не разрешаются.
- Внешние/отсутствующие, неоднозначные и неразобранные зависимости дают
  предупреждения. Симлинки и Windows reparse points не обходятся. Каталоги
  `.git`, `target`, `node_modules`, `.venv`, `venv`, `__pycache__` исключены.
  Исходники должны иметь UTF-8 кодировку. Cross-language FFI не анализируется.

## Проверки

```text
cargo fmt --manifest-path analyzer-rs/Cargo.toml --check
cargo clippy --manifest-path analyzer-rs/Cargo.toml --all-targets --locked --offline -- -D warnings
cargo test --manifest-path analyzer-rs/Cargo.toml --locked --offline
```

Интеграционные тесты создают временные репозитории и проверяют Rust/Python,
неоднозначности, нормализацию путей, кратчайшие расстояния, циклы, ошибки и
точную форму JSON через настоящий CLI-процесс. Unix-тест дополнительно
проверяет, что симлинки наружу и циклические симлинки не обходятся.
`Cargo.lock` закреплён в репозитории; `target/` исключён из Git.

## Цепочки и сравнение снимков (совместимое расширение v1)

Старый запрос с `protocol_version`, `repo_path`, `changed_files` продолжает
работать. Новые входные поля необязательны: `baseline_repo_path` — **абсолютный**
путь к независимому локальному снимку до изменений; `changes` — массив объектов
`{path, status, old_path?}`. Допустимые статусы: `added`, `modified`, `deleted`,
`renamed`. Для `renamed` обязателен `old_path`, а `path` обозначает новое имя.
Остальные статусы не допускают `old_path`. Все пути изменений относительные.
Повторные/противоречивые записи одного старого пути переименования отклоняются.

`changed_files` можно передать вместе с `changes` или опустить. Анализируется
объединение этих путей, включая оба конца переименования. Статусы — сведения
от вызывающей программы, а не доказательство изменения: несовпадение с
читаемыми файлами снимков отмечается в limitations. Переименование не
угадывается по сходству содержимого: нужна явная запись `renamed`.

Новые выходные поля: `affected_files[].chain` и `impact` с массивами `findings`
и `limitations`. Они всегда выдаются этой реализацией, но клиент должен
допускать их отсутствие в ответах старого анализатора. Старые поля сохраняются.
Без baseline выдаются текущие цепочки и объяснение невозможности сравнения,
но не выдумываются находки об удалениях или изменённых API.

Цепочка направлена **от затронутого файла к изменённому**, включает оба конца,
и имеет длину `distance + 1`. Среди кратчайших маршрутов выбирается
лексикографически минимальный массив путей (Rust String ordering, независимо
от локали). Расстояния строго убывают вдоль цепочки: циклы не приводят к
зацикливанию. Сам изменённый файл не попадает в affected_files; при нескольких
изменениях выбирается ближайший, а при равенстве — та же лексикографическая
политика. Отсутствующие файлы не отображаются как затронутые, но могут быть
концом исторической цепочки. Одна связь сама по себе не означает поломку.

Точные условия находок первой версии:

| code | Условия | severity / confidence |
| --- | --- | --- |
| `deleted_dependency` | Baseline разрешил локальный `mod`/`use`/`import`/`from` в конкретный файл; цель входит в набор изменений и отсутствует в текущем снимке; импортирующий файл существует и в его AST остаётся тот же импорт. Нет применимой явной записи переименования с существующей новой целью. | `high` / `confirmed` для подтверждённого статического перехода; `warning` / `possible` при неполноте разбора или другом текущем связывании. |
| `renamed_dependency` | Те же условия отсутствия старой цели и сохранения импорта; вызывающая программа явно указала `renamed`, а новый файл существует. Импорт, обновлённый на новый путь, не создаёт эту находку. | Та же политика. Подтверждается сохранённый старый импорт и файловый переход по данным caller, а не тождество модулей или runtime-ошибка. |
| `public_symbol_changed` | Baseline содержит прямой именованный импорт символа из изменённого файла; тот же импорт остаётся в текущем AST; публичная декларация в baseline однозначна; в текущем файле её нет, она стала приватной либо её представление изменилось. Оба файла определения должны разбираться. | Всегда `warning` / `possible`: требуется проверка использования символа; изменение сигнатуры может быть совместимым. |

Для Rust сравниваются `pub` и ограниченные `pub(...)`: сигнатуры функций
(без тела), объявления struct/enum/type/const/static/trait в токенизированном
виде; inline-модули обходятся, одноимённые неоднозначные декларации пропускаются.
Тела методов trait входят в его представление и могут дать консервативный вывод.
Для Python проверяются функции, async-функции и классы верхнего уровня с именем
без начального `_`: текст заголовка до первого оператора тела с нормализованными
пробелами. Тела функций не сравниваются. Методы, поля классов Python, assignments,
декораторы, реэкспорты и динамическое связывание не сравниваются; комментарии в
заголовке или defaults могут давать консервативные изменения. Без прямого
именованного импорта (например, только `import helpers; helpers.run()`) сравнение
символов не делает вывода о `run`.

`confirmed` означает подтверждение перечисленных статических фактов, **не**
гарантию сбоя программы. `high` — приоритет проверки импорта, `warning` — повод
проверить возможное изменение; значение `info` зарезервировано контрактом и
этой версией не генерируется. `paths` перечисляет конкретные файлы: importer,
старая цель, а для rename — ещё новая цель. `evidence` содержит импорт, имя и
представления символа до/после (для API), ограничение и рекомендацию проверки.

Неполнота любого снимка (ошибки чтения/синтаксиса, namespace packages,
макросы/cfg и другие ограничения resolver) понижает уверенность файловых
находок до `possible`. Обычное неразрешение внешнего/пропавшего импорта само
по себе этого не делает. Все общие сообщения остаются в `warnings` и отдельно
перечисляются в `impact.limitations` (baseline с префиксом `Baseline:`).
Импорты `std`, `serde`, `os` и других внешних пакетов сами по себе **никогда
не создают finding**. Изменения, не включённые в changed_files/changes,
не проверяются на удаление/API; Git diff и история не запрашиваются.

Пример ответа для Python-агента: в baseline было `runner.py → app.py → helpers.py`,
теперь `helpers.py` удалён, а `app.py` сохраняет `import helpers`. Запрос:

```json
{
  "protocol_version": 1,
  "repo_path": "/snapshots/current",
  "baseline_repo_path": "/snapshots/before",
  "changes": [{"path": "helpers.py", "status": "deleted"}]
}
```

Ответ (общие диагностические строки показаны сокращённо):

```json
{
  "protocol_version": 1,
  "changed_files": ["helpers.py"],
  "affected_files": [
    {"path": "app.py", "distance": 1, "reason": "depends on changed file", "chain": ["app.py", "helpers.py"]},
    {"path": "runner.py", "distance": 2, "reason": "depends on changed file", "chain": ["runner.py", "app.py", "helpers.py"]}
  ],
  "edges": [
    {"from": "app.py", "to": "helpers.py", "relation": "imports"},
    {"from": "runner.py", "to": "app.py", "relation": "imports"}
  ],
  "warnings": ["app.py: Cannot resolve Python import helpers locally (external/missing module or unsupported search path)"],
  "impact": {
    "findings": [{
      "code": "deleted_dependency", "severity": "high", "confidence": "confirmed",
      "paths": ["app.py", "helpers.py"],
      "evidence": "app.py: import helpers. Previously imported local file is absent from the current snapshot. Both snapshots confirm the file transition and unchanged import syntax. Check this import and dependent tests; no project code was executed."
    }],
    "limitations": ["Historical targets in edges/chains need verification; findings are static evidence, not proof of runtime failure."]
  }
}
```

Python-клиент читает поля безопасно: `result.get('impact', {}).get('findings', [])`
и `file.get('chain', [])`. Для показа пользователю цепочки можно использовать
`' → '.join(file.get('chain', []))`. Baseline должен оставаться неизменным во
время анализа; файлы репозитория не запускаются, временные checkout, API и
сетевые запросы анализатор не создаёт.

## 0.0.3: предварительная оценка и папки Python

Для оценки **до редактирования** передайте существующий файл в `changed_files`,
без `baseline_repo_path` и `changes`. Это гипотетический выбор файла, а не
утверждение о сделанной правке. `affected_files` и `chain` покажут область
потенциального влияния; конкретные поломки без изменения кода не предсказываются.

Совместимые дополнительные поля ответа v1:

- `analyzer_version`: версия реализации (`0.0.3`; прежнее `0.1.0` было версией
  crate, теперь номер согласован с тестовой версией приложения).
- `files`: отсортированные читаемые `.py` и `.rs`, в том числе без связей.
  Наличие файла не гарантирует успешного разбора: проверяйте `warnings`.
- `current_edges`: только связи текущего снимка, до восстановления исторических
  зависимостей. Для предварительного просмотра используйте именно этот граф.
  `edges` по-прежнему содержит граф сравнения, включая исторические связи.

В корне анализируемого репозитория можно сохранить `.impactmap.json`:

```json
{"python_source_roots": ["desktop-py", "services/backend"]}
```

Папки добавляются к корню репозитория и `src/`. Пути относительные; выход за
репозиторий запрещён. При неоднозначности импорт не угадывается. Для относительных
импортов используется самый вложенный подходящий корень. Конфигурация читается
отдельно из каждого снимка; неверная конфигурация даёт предупреждение и стандартные
корни. Это декларация путей импорта, код и `sys.path` не исполняются.

## 0.0.4: исправление ложных предупреждений

`warnings` теперь содержит диагностируемые проблемы, а обычные ограничения
разрешения символов, namespace packages, макросов, cfg и реэкспортов находятся
в `impact.limitations`. Ограничения не удалены из отчёта: они по-прежнему
понижают уверенность сравнения снимков. Старые упоминания предупреждений об этих
общих ограничениях выше следует читать как `impact.limitations`.

Изменённый Markdown или другой неподдерживаемый тип файла остаётся в
`changed_files`, но не считается отсутствующим исходником. Для него выдаётся
информационное ограничение покрытия.

Известные внешние импорты не требуют локального файла и не дают предупреждения:

- Rust: `std`, `core`, `alloc`, `proc_macro` и имена зависимостей из ближайшего
  `Cargo.toml`, включая aliases, dev/build и target-зависимости. `path`-зависимости
  остаются локальными: их ошибки не скрываются.
- Python: фиксированный список имён стандартной библиотеки CPython 3.13
  (`src/python_stdlib.txt`, получен из `sys.stdlib_module_names`) и имена из
  `requirements*.txt` / `[project].dependencies` в `pyproject.toml`. Для простого
  сопоставления регистр не учитывается, дефис заменяется на `_`. Distribution
  name и import name могут различаться — такие случаи остаются неразрешёнными.
  Python не запускается для классификации импортов во время анализа.

Локальные файлы и неоднозначные локальные кандидаты проверяются раньше внешней
классификации; затенение внешнего имени не скрывает ошибку локального импорта.
Неизвестные импорты, отсутствующие локальные `mod`, ошибки синтаксиса, неверная
конфигурация и недоступные исходники сохраняют предупреждения. Наличие имени
во внешних зависимостях не доказывает, что пакет установлен или его API корректен:
это локальный граф исходников, а не проверка окружения исполнения.

Регрессия воспроизведена на снимке ImpactMap
`4cbb53c94df12224717278ffe7ea7cf33187bb1b`: старый бинарник выдавал **120**
предупреждений, версия 0.0.4 выдаёт **0**, при этом находит 32 локальные связи.
Каталог `desktop-py/` разрешается через существующую `.impactmap.json`.
Ограничения покрытия остаются доступны отдельно и не означают ошибки программы.
